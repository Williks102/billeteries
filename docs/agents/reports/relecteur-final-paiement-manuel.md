## Importants
- I-A [VÉRIFIÉ, logique] Plafond GLOBAL de 50 billets pending par événement : app/Services/CheckoutService.php:191-205 (défaut config/payments.php `max_pending_tickets_per_event` = 50). Avec un paiement manuel qui laisse des commandes pending 24-48 h, tout événement qui a 50 billets non encore réglés refuse TOUS les nouveaux acheteurs, avec LIMIT_ERROR (« Réglez vos commandes en attente… », l.27) trompeur pour un acheteur qui n'a rien en attente. Un attaquant (1 IP : 10 commandes invité × max_per_order) gèle la vente d'un événement pour 24 h, renouvelable : le correctif anti-accaparement devient un déni de vente bon marché. securite recommandait « ≤ 20-30 % du stock » (securite-correctifs-paiement-manuel.md:17), non suivi. Correctif : plafond relatif à la capacité de l'événement (ex. % de la somme des quantity_available) + plafond de BILLETS par email/compte/IP ; message distinct ; décision métier du propriétaire sur la valeur. Agent : paiements-stock (+ propriétaire). Convergent avec securite N-B (trouvé indépendamment).
- I-B [SUPPOSÉ : sémantique InnoDB REPEATABLE READ, pas de MySQL dans l'environnement] Le comptage « sous verrou » lit un instantané périmé. CheckoutService.php:193-199 : le SUM est une lecture non verrouillante ; dans le checkout invité, `User::where('email')->first()` (GuestCheckoutController.php:149, dans la même transaction, l.70-74) fixe l'instantané AVANT le `lockForUpdate` sur events. Une 2e requête attend le verrou puis compte sans voir les billets commités par la 1re : le plafond est franchissable en parallèle, exactement le cas visé. Même effet pour le 2e événement d'un panier multi-événements (connecté ou invité). Le test test_the_cap_check_runs_inside_the_reservation_transaction (SQLite) ne peut pas le voir. Correctif : `->lockForUpdate()` (ou `sharedLock()`) sur la requête SUM, ou compteur agrégé sur events mis à jour sous verrou ; test MySQL à 2 connexions. Agent : paiements-stock + qa-tests. Ne bloque pas (supposé). Convergent avec securite N-A.
- I-C [VÉRIFIÉ] CGU contradictoires laissées en place : resources/views/pages/terms.blade.php:212 (« non livraison plus de deux (2) heures après la commande » ⇒ résolution et remboursement) alors que les billets ne sont émis qu'après confirmation manuelle (l.210, réservation 24-48 h) : chaque commande ouvre ce droit contractuellement. Aussi l.214 (7 jours depuis l'achat). Listé par ui-design (rapport §1-2) mais publié tel quel. Correctif : faire courir le délai à compter de la confirmation du paiement (proposition ui-design §1). Agent : propriétaire (décision), puis ui-design.

## Mineurs
