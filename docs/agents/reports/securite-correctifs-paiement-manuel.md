## Nouveaux constats
### Élevé
- N1. Prise de contrôle préventive de compte (account pre-hijacking). Scénario : l'attaquant commande en invité avec l'email d'une victime inconnue du système => le compte invité est créé par SA commande (la plus ancienne), il garde la preuve de session C1, appelle create-account avec son mot de passe (GuestCheckoutController.php:180-227 : conditions toutes vraies) => compte non invité, mot de passe connu de lui, email_verified_at null mais aucun contrôle de vérification. Quand la victime commande ensuite (invité ou connecté, même email), findOrCreateGuest rattache la commande à ce compte (l.147-150) : l'attaquant se connecte et voit/télécharge les billets payés. La victime ne peut pas s'inscrire (unique:users). Correctif : preuve de possession de l'email avant toute conversion (lien signé envoyé à l'email, mot de passe défini via ce lien) ; sinon, ne jamais rattacher de nouvelles commandes à un compte dont email_verified_at est null et is_guest=false (créer un nouveau compte invité impossible car unique : donc refuser/faire passer par reset password) ; ou activer MustVerifyEmail + middleware verified sur espaces acheteur/billets. Agent : paiements-stock (+ propriétaire Auth).
- N2. TrustProxies non configuré (bootstrap/app.php : aucun trustProxies ; déploiement non documenté). Derrière un reverse proxy/LB, request->ip() = IP du proxy : (a) throttle checkout 10/min partagé par tous les invités du site ; (b) plafond guest 10 commandes/24 h (CheckoutService.php:106-110, 128-140) devient GLOBAL : après 10 commandes invité, plus aucun invité ne peut commander pendant 24 h (DoS involontaire, ou volontaire en 10 requêtes). Même sans proxy, le CGNAT des opérateurs mobiles ivoiriens fait partager une IP à beaucoup d'acheteurs. Correctif : trustProxies(at: env('TRUSTED_PROXIES')) (jamais '*' si le proxy ne réécrit pas XFF), documenter dans .env.example, tester ; reconsidérer le plafond IP (par ex. 10 -> 30, sur 1 h). Agent : devops-hygiene (bootstrap/app.php) + paiements-stock.
- N3. Accaparement de stock encore possible. Chiffrage : invité, 1 IP : 10 commandes/24 h (la fenêtre minute du throttle n'est pas limitante) x jusqu'à 10 billets par ligne x nb de types du panier = >=100 billets/IP/jour pour 1 type (rotation d'IP/proxys/IPv6 : multiplicatif). Connecté : le plafond IP ne s'applique pas (guest seul, l.106) ; 3 pending/compte x 10 billets = 30 par compte pendant 48 h ; register sans throttle ni vérification d'email (routes/web.php : seul throttle:60,1 l.124 hors auth) => N comptes jetables, chacun à 10 req/min : stock vidable par script sans limite pratique (~30 billets/compte/min). Contrôles non atomiques : check (assertWithinOrderLimits) puis hit après coup, sans verrou : 10 requêtes parallèles avec le même panier de session passent avant tout comptage (borné par le throttle 10/min, mais x nb d'événements du panier). Email : lower+trim mais alias +tag/points non normalisés (compensé par le plafond IP côté invité seulement). Correctif : throttle sur register (ex. 5/min/IP) + vérification d'email obligatoire avant checkout connecté ; plafond global par événement de billets pending non payés (ex. <=20-30 % du stock) ; compter les hits dans la transaction (verrou) ; ne plus faire confiance au cache database seul (CACHE_STORE=database : OK mais non atomique). Agent : paiements-stock.
### Moyen
- N4. Rattachement d'une commande tierce au compte existant (findOrCreateGuest l.147-150) : n'importe qui peut ajouter des commandes pending à l'historique de la victime et déclencher des emails d'instructions (F1) ; borné par 3 pending/email et 24-48 h. Si l'admin confirme un paiement, la victime reçoit billets + PDF (sendPaymentConfirmation -> user->email). Correctif : pour un compte existant non invité, créer la commande avec guest_token et user rattaché mais ne pas l'afficher dans l'historique avant paiement, ou la rattacher seulement après confirmation par email. Agent : paiements-stock.
- N5. Écart de timing email connu/inconnu (voir E1). Correctif : Hash::make toujours exécuté (ou password non haché, ex. Str::random bcrypt-free via Hash::make déplacé hors branche) ; déplacer création de compte invité en file/après réponse. Agent : paiements-stock.
### Faible
- N6. refund() annule tous les billets du lot y compris `used` (scannés) et libère le stock (OrderPaymentService.php:198-199) : décision métier, au moins journaliser/bloquer si billets used. Agent : paiements-stock + architecte.
- N7. Admin/OrderController.php:~385 bulk resend_emails appelle sendPaymentConfirmation (retourne false silencieusement) ; le compteur « traité » compte un échec d'envoi. Cosmétique.
