## Constats

### Élevé
- E1. Prise de contrôle d'un compte invité par email. GuestCheckoutController.php:~150-165 : si l'email correspond à un User is_guest, `create_account=1` + mot de passe attaquant => forceFill(password, is_guest=false) + auth()->login, sans preuve de possession de l'email (aucune vérification). Avant ce commit la branche était inerte (is_guest jamais enregistré, non fillable) ; forceFill l'a activée : régression introduite. Exploitation : saisir l'email d'une victime ayant déjà acheté en invité, obtenir un compte connecté avec l'historique (billets, commandes). Même sans create_account, la branche « mise à jour invité existant » écrase nom/téléphone du invité (altération de PII) et rattache la commande à son compte. Correctif : ne jamais convertir/modifier un invité existant sans preuve (lien email signé) ; pour create_account sur email déjà connu, refuser avec message générique ou envoyer un lien de vérification ; ne pas réécrire name/phone d'un invité existant ; email_verified_at null pour tout compte créé ici. Idem createAccountAfterPurchase (l.~270) : `update(['is_guest'=>false])` est ignoré (non fillable) donc l'utilisateur reste is_guest=true ; utiliser saveUser/forceFill. Agent : paiements-stock (+ propriétaire de User.php pour $fillable/colonnes).
- E2. Accaparement de stock anonyme. Aucun throttle sur POST checkout/guest/process (routes/web.php:101-106 ; seul 'throttle:60,1' ligne 120 ailleurs), réservation manuelle de 48 h (config/payments.php:11), jusqu'à 10 billets par ligne : un script vide le stock d'un événement sans payer pendant 48 h. Correctif : throttle (ex. 5/min/IP) sur guest/process et checkout/process, plafond de commandes `pending` par email/IP/user (ex. 3), réduire manual_reservation_minutes, captcha. Agent : paiements-stock (+ devops).

### Moyen
- M1. update()/updateStatus()/bulkAction mark_failed mettent failed/refunded, annulent les billets (`status=cancelled`) mais ne libèrent pas quantity_sold (OrderController update ~l.140-150, updateStatus ~l.185, bulk mark_failed ~l.370 ; refund() aussi). Admin seul : stock définitivement faussé (invendable), et un confirmPayment ultérieur d'une telle commande `failed` fait reclaimStock => double comptage. Correctif : pending/processing => failed uniquement via `$order->releaseStock()` ; paid => refunded via refund() (décider si on libère le stock) ; sinon refuser. Agent : paiements-stock.
- M2. Machine d'états ouverte pour l'admin : update/updateStatus acceptent n'importe quelle transition (paid->pending, refunded->pending, puis ->paid contourne le refus « refunded » de confirmPayment et remet en `sold` des billets annulés sans reréserver le stock ; paid->failed laisse la commission). Correctif : table de transitions autorisées (pending|processing->paid|failed, paid->refunded, failed->paid via service) centralisée dans Order/OrderPaymentService ; annuler/neutraliser la commission sur failed/refunded. Agent : paiements-stock + architecte.
- M3. Fuite d'information à l'inscription invité : `back()->with('error','Erreur: '.$e->getMessage())` (GuestCheckoutController.php:~95) renvoie « Un compte existe déjà avec cet email » (énumération d'emails) et des messages internes (SQL) possibles. Correctif : message générique pour les \Exception non métier, journaliser. Agent : paiements-stock.

### Faible
- F1. Email d'instructions envoyé à `billing_email` saisi librement (spam/harcèlement vers un tiers, une commande par événement). Throttle (E2) + message neutre.
- F2. Logs checkout invité contiennent l'email en clair (Log::info 'Début handle user invité', 'email'). Retirer ou hacher.
- F3. update() branche paid : `admin_notes` non enregistré ; bulk mark_paid avale l'OrderPaymentException sans retour utilisateur. Cosmétique.
- F4. Commission créée à la commande (même impayée/failed) : vérifier que les paiements promoteur ne se basent que sur commandes `paid` (hors périmètre, à confirmer par architecte).
- F5. Pas de test de concurrence MySQL sur la double confirmation (qa-tests).
