## Nouveaux constats
### Élevé (mise en production, pas la fusion)
- N-B. Le plafond 50 billets pending par événement est GLOBAL (CheckoutService.php:196-203) : 1 IP + 5 commandes de 10 billets (ou 3 emails) suffit à geler toute la vente d'un événement pendant 24 h (invité) / 48 h (connecté), renouvelable ; inversement un lancement populaire refuse le 51e acheteur légitime avec un message neutre trompeur. Stock bloquable : borné à 50 billets/événement quel que soit le nombre d'IP/comptes (c'était illimité avant), mais le coût d'attaque est bas. Acceptable pour un MVP à faible trafic, pas pour de vrais paiements sans parade : (1) cap exprimé en % du stock (ex. 20 %) ET plafond de billets par email/compte/IP (ex. 6-10), pas seulement en commandes ; (2) vérification d'email avant toute réservation (envoi du lien, réservation courte 2 h tant que non vérifié) ; (3) captcha/Turnstile sur checkout invité et register ; (4) alerte admin si cap atteint + annulation manuelle (admin/orders failed). Agent : paiements-stock (+ propriétaire pour la décision métier).
### Moyen
- N-A. Le comptage sous verrou lit un instantané périmé sous MySQL REPEATABLE READ : dans le checkout invité, `User::where(...)->first()` (non verrouillant) s'exécute AVANT `lockForUpdate` sur events, ce qui fixe l'instantané ; le SUM suivant (l.198-203) ne voit pas les commits concurrents (même chose pour le 2e événement d'un panier multi-événements). Le verrou sérialise mais ne protège pas : le plafond reste contournable en parallélisme. Correctif : ajouter `->lockForUpdate()` (ou `sharedLock`) à la requête SUM (lecture verrouillante = dernières données) ou compter via une colonne agrégée sur events mise à jour sous verrou ; test MySQL réel (2 connexions). Agent : paiements-stock + qa-tests.
- N-D. Déni d'achat ciblé : les commandes d'un tiers rattachées au compte victime (billing_email = email victime, user_id = victime) comptent dans son quota de 3 pending (assertWithinOrderLimits, CheckoutService.php:92-100) : 3 requêtes bloquent la victime 24 h, renouvelable. Correctif : pour un checkout connecté, ne compter que `user_id = X AND guest_token IS NULL` (et ne pas matcher billing_email sur les commandes à guest_token) ; filtrer aussi le dashboard/stat acheteur avec visibleInBuyerHistory (AcheteurController.php:32,53, Acheteur/OrderController.php:66-75, profile.blade.php:128-141). Agent : paiements-stock.
### Faible
- N-C. Deadlock possible : verrous events -> ticket_types pris dans l'ordre du panier (pas trié) ; paniers A,B vs B,A -> deadlock InnoDB, une transaction avortée (erreur générique, retry). Pas de cycle avec confirm/fail/refund/expiration (commande -> types, jamais events). Correctif : `ksort($groups)` dans buildEventGroups. Agent : paiements-stock.
- N-E. TRUSTED_PROXIES contenant la valeur littérale `REMOTE_ADDR` ou `0.0.0.0/0` = confiance totale (comportement Laravel/Symfony ; erreur d'opérateur) : refuser ces valeurs dans TrustedProxyConfig. Agent : devops-hygiene.
- N-F. Forgot-password non throttlé (bombardement d'emails de reset) et énumération ; email de reset/inscription loggués. Agent : devops-hygiene.
- N-F3 (ops). Avec config:cache et sans variable d'environnement réelle, aucun proxy de confiance : derrière un LB, register (5/min) et plafond IP (10/24 h) deviennent globaux (DoS involontaire). Ajouter à la checklist de déploiement et à un contrôle au démarrage. Agent : devops-hygiene.
